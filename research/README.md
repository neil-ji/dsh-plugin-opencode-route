# Route 效果：基线、方法与 A/B

这份笔记回答一个问题：**这个插件的选道，能不能用数据证明有效**。它在 install 之前写成，因此基线部分只用本机已有的 durable session log，不依赖插件。

结论先行：

1. **基线比插件 README 的动机描述好得多**。446 个会话、44k 次调用里，会话中位 151 tok/s，只有 2% 的会话低于 70 tok/s；没有看到"4/8 个 id 永远 429"的证据（重试在持久日志里不可见，所以这是下界）。
2. **完美选道的收益上界是 1.33×**（从经验分布里挑 4 条中最好的，零成本、零误判）。
3. **前后对比不够用**：在没有插件的情况下，按日期任意切一刀，就会得到 **0.92–1.06×** 的表观效应（SD 0.044），与要测的效应同量级；而且它无法排除同期任何其他变化。
4. **正确做法是同期随机双臂**：`experiment.enabled: true` 按会话 id 的稳定哈希分桶，control 不探测也不换道。实测产出 27 会话/天，一周约 190 个会话 → 95/臂，能检出 **1.15×**；两周能到 1.1×。

## 1. 数据来源与口径

- **来源**：`~/.dsh/sessions/*/session.v{3,4}.jsonl.zstd`（多帧 zstd）。`assistant/message` 事件里保存了完整的 chunk 流：`time0` + `dt[]`，因此可以逐条重建时间。
- **口径**（与插件的 `turn` 事件相同，便于事后交叉校验）：

  ```
  ttfb   = 首个 token 时间 − step/start 时间
  decode = 最后一个 token 时间 − 首个 token 时间
  tps    = outputTokens × 1000 / decode
  ```

  插件从 1.7.3 起在 `turn` 事件里直接写 `decodeMs`，所以 A/B 报告能用和历史完全相同的过滤条件。

- **合格调用**：`output ≥ 60` token 且 `decode ≥ 300 ms`（去掉短回答和突发式流造成的不可测样本，与插件自身的 `measured` 规则同向但更宽松）。
- **统计单位**：会话。同一会话的多次调用高度相关，按请求算会把 n 虚增上百倍。

复现：

```bash
node research/collect_sessions.mjs     # ~15s，写出 out/calls.jsonl
node research/analyze_baseline.mjs     # 打印下面全部基线
```

## 2. 基线（2026-10-22 → 11-08）

```
446 sessions · 44,270 calls · 41,759 usable · 405 sessions with >=3 usable
45,092 steps → 822 无产出 (1.8%)
turn/end: completed 1296 · aborted 30 · error 15 · interrupted 9
```

| | p10 | p25 | p50 | p75 | p90 |
|---|---|---|---|---|---|
| 调用级 tps | 97 | 124 | **158** | 195 | 241 |
| 会话级中位 tps | 106 | 130 | **151** | 171 | 188 |

- TTFB：p10 2,761 ms · p50 **4,231 ms** · p90 8,713 ms
- 输入规模：p50 **147,245** token · p90 402,897 token；缓存命中 p50 **99%**
- 会话速度分层：<70 tok/s **2%** · 70–150 **46%** · ≥150 **51%**

日表中位在 132–208 tok/s 之间摆动。注意这和"日间效应"不是一回事：日表按调用聚合，受当天会话构成影响；按会话中位做两层分解后，日间 SD(log) 只有 0.09。

## 3. 方差分解与功效

把 `log(tps)` 分解成"会话之间"与"会话之内"：

```
between-session SD(log) 0.26 · within-session SD(log) 0.39 · ICC(1) = 0.30
```

ICC=0.30 的含义：**约三成的速度方差来自"这个会话从哪条路由开始"，其余是请求本身的噪声**。这就是可优化空间的上界来源。

从经验分布模拟"挑 4 条中最好的"（无缓存代价、零误判）：**1.33×**。这是理论上限，真实选道会低于它（探针只有 96 token、有选择偏差、换道要付 re-prefill）。

功效（会话级，双侧 α=0.05，power=0.8，SD(log)=0.27）：

| 效应 | 需要会话数/臂 |
|---|---|
| 1.35× | 13 |
| 1.20× | 34 |
| 1.15× | 58 |
| 1.10× | 124 |

## 4. 为什么不用"装前 vs 装后"

用同一份没有插件的基线，按日期切分、把后段当作"处理期"，得到的表观效应：

```
cut 2026-10-28: pre  41 post 364 → 0.92x
cut 2026-11-01: pre  64 post 341 → 1.03x
cut 2026-11-02: pre 102 post 303 → 1.06x
cut 2026-11-04: pre 228 post 177 → 0.96x
cut 2026-11-06: pre 309 post  96 → 0.92x
               范围 0.92–1.06x，标准差 0.044
```

也就是说：**什么都不做，前后对比也能给出 ±6% 的结论**。再叠加两件事：

- 一周的 post 期只有约 190 个会话，比值本身的 95% CI 约 ±5%；
- 上游负载、模型版本、你的使用构成在这段时间里并不同质（日表中位摆幅 132–208）。

所以前后对比只能当**粗筛**：只有效应 ≥1.15× 且同期确实没有别的变化时才可信。它不能回答"插件值不值"。

## 5. A/B 设计

```yaml
experiment: { enabled: true, armRatio: 0.5, salt: route-v1 }
```

- **分桶**：`sha256(salt:sessionId)` 的前 4 字节 / 2³² < `armRatio` → treatment。确定性、跨重启稳定、同一会话不会换臂。
- **treatment**：正常探测 + 钉住。
- **control**：不探测、不读池、不打 header。它必须等于"没装插件"，否则探针的 token 与延迟会污染对照。
- **指标**：会话级合格调用的 `tps` 中位数（主）；TTFB 中位数、缓存命中、错误率（次）。
- **分析**：day 分层 bootstrap（在每个日期内分别重采样两臂的会话），日漂移在比较中被抵消。

```bash
node research/analyze_ab.mjs --baseline research/out/calls.jsonl
```

- **预注册判据**：
  - `treatment/control` 中位比值 95% CI 下界 > **1.05**，且 TTFB 不劣化 → 有效；
  - CI 上界 < 1 → 负向（检查 `SHAPE_RANK` 与缓存代价）；
  - CI 跨 1 → "当前数据不支持"，补样或停用。
- **完整性检查**：脚本会验证 control 组里没有任何 `probe` 事件、没有任何 `pin`。这依赖 1.7.3 起 `probe*` 事件带 `sessionId`。
- **样本量**：一周 190 会话 → 95/臂，可检出 1.15×；两周 190/臂，可到 1.1×。

## 6. 与插件假设冲突的三个观察

**a. `SHAPE_RANK` 的方向与数据相反。** 插件把 `gw` 排第一、`chatcmpl` 排最后，且 `gw` 免测速：

| shape | calls | p25 | p50 | p75 |
|---|---|---|---|---|
| gw | 14,598 | 113 | **137** | 169 |
| hex48 | 11,668 | 151 | **178** | 212 |
| hex32 | 7,653 | 143 | 172 | 207 |
| chatcmpl | 7,671 | 94 | 144 | 195 |

跨会话比较有混杂（形状与时段相关），但按天看 `hex48 > gw` 也在多数可比日成立。至少可以确定：**"gw 最快"这个前提没有数据支撑，而它正是 `admittable()` 里唯一免测速的通行证**。

1.7.4 已按这条结论改掉：`gw` 不再免测放行，排序按实测分数，不可测的窗口用 `out × 2` 的下界参与排序，形状只做最后一级 tie-break。

**b. `responseId` 不是路由指纹。** 每个会话的不同 `responseId` 数 p50=68（≈每请求一个），只有 3% 的会话是单一 id。所以"同一 id → 同一上游"无法从日志验证，只能用重复探针测。

**c. TTFB 由上下文规模主导。** 输入 p50 14.7 万 token、缓存命中 99%，TTFB 中位 4.2 s。路由对 TTFB 的杠杆很小；换道的代价却是要把这 14.7 万 token 重新 prefill 一次。插件的价值集中在**长输出的解码速度**，而不是"看起来更快出字"。

另外：**历史日志量不出失败率**。429 会在同一个 step 内重试，重试成功就不留痕迹；只有 822 个无产出 step（1.8%）和 15 个 error turn 能作为下界。要量失败率，只能靠插件自己的 `turn.finish`/`failure` 字段。

## 7. 局限

- 全部数据来自**这一台机器、一个 profile、18 天**；上游行为可能随 OpenCode 的部署变化。
- chunk 时间戳是**到达时间**，包含网络抖动；后台抽帧、压缩等系统负载会放大噪声，这已计入 within-session SD。
- `tps` 的口径是"输出 token / 首末 token 间隔"，包含推理 token；不同模型的构成不同，所以**只在同一模型内比较**。
- 样本里 46% 的会话落在 70–150 tok/s 区间，这正是插件主要能改善的地方；<70 的只有 2%，所以"救活死会话"不是当前的主要价值。
